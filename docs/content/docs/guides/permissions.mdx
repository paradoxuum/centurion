Centurion uses a role-based permission system. Roles have an optional set of named permissions, and can inherit from other roles.
A player can be assigned multiple roles, and can run a command if any of their roles satisfies the command's requirements.

## Creating Roles

Define roles with `create_role`. A role that `inherits` from another gets all of its permissions, and counts as that role wherever it's
required. Inheritance is transitive: `admin` below inherits from `moderator`, so it also inherits from `user`.

Roles that don't inherit from each other are independent, so a `builder` role can grant building permissions without moderators getting
them too. A role can inherit from several roles at once.

Each role name can only be registered once, and a role must be created before any role that inherits from it and any command that requires it.

centurion.create_role("admin", { inherits = { "moderator", "builder" } })

create_role("admin", { inherits: ["moderator", "builder"] });

### Editing Roles

`update_role` changes a role's permissions or what it inherits. Pass only the fields to replace. Roles that inherit from it, and the
players who have it, see the change straight away.

### Deleting Roles

`delete_role` removes a role and takes it away from every player who has it. A role that other roles inherit from, or that's a default
role, can't be deleted until those are removed first. A command that still requires a deleted role can't be run by anyone.

## Restricting Commands

Commands can require a specific **role** or a specific **permission**.
Either restriction can be used independently or together.

Roles are only assigned and checked on the server, so restricted commands must be registered on the server. Registering a command with
`roles` or `permissions` on the client is an error.

Both lists are **any-of**: the player needs one of the listed roles or one of the listed permissions, not all of them. A command listing both passes if either check succeeds.

## Managing Player Roles

local Players = game:GetService("Players")

centurion.set_roles(player, { "moderator" })

centurion.add_roles(player, "moderator")

centurion.remove_roles(player, "moderator")

local roles = centurion.get_roles(player)

if centurion.has_permission(player, "kick") then

end

### Loading Saved Roles

Roles are usually loaded from a DataStore when a player joins. Since default roles are kept separately (see below), `set_roles` only
replaces the roles you saved, and `get_roles` returns exactly what you should save back.

If the player leaves before their roles finish loading, `set_roles`, `add_roles` and `remove_roles` do nothing for them, so a slow load
can't leave roles behind for a player who's gone.

## Default Roles

Give every player a set of roles with `set_permission_options`. Default roles apply to all players, including ones already in the game,
on top of whatever roles they've been assigned. They aren't stored as part of a player's roles, so `set_roles` and `remove_roles` don't
affect them and `get_roles` doesn't include them. Changing the default roles updates every player's synced commands.

## Hiding Unauthorized Commands

By default (`hide = true`), commands that a player cannot execute are hidden silently - no error is shown.
Set `hide` to false if you want to display an explicit "no permission" error instead.

With the built-in networking, `hide` also controls which commands are synced to each client: a hidden command never reaches the client
at all, and is synced or removed as the player's roles change.

## Denying Unrestricted Commands

By default, a command without `roles` or `permissions` can be executed by everyone. Set `deny_unrestricted` to make such commands
unexecutable instead, so a command that's missing its restrictions is locked down rather than open to all players. This only applies
on the server, so commands registered on the client keep working.

## Class Decorators (TypeScript)

Apply `@Role` or `@Permission` to a class or individual methods.

```ts
import { Command, Group, Role, Permission, register_classes, args } from "@rbxts/centurion";
import type { ExecutionContext } from "@rbxts/centurion";

@Group("mod")
@Role("moderator")      // all methods require the moderator role
class ModCommands {
    @Command({ description: "Kick a player", arguments: () => [args.player("target")] })
    kick(ctx: ExecutionContext, target: Player) {
        target.Kick();
        ctx.reply(`Kicked ${target.Name}`);
    }

    @Permission("ban")  // players with the "ban" permission can also run this
    @Command({ description: "Ban a player", arguments: () => [args.player("target")] })
    ban(ctx: ExecutionContext, target: Player) {
        // ...
    }
}

register_classes();
```

Decorators on a method add to the ones on its class rather than replacing them. Since roles and permissions are any-of, `ban` can be run
by moderators (from the class's `@Role`) **or** by anyone with the `ban` permission. To restrict a command further than its class, put it
in a separate class.

Player cleanup (removing role data on disconnect) is handled automatically by the permission module.
